# Native binary analysis

This method needs reverse.native in the task's moduleSelection. Use the supplied adapter route; read security_capabilities only for missing capability or routing information. The coordinator may update automatic selections through security_command action modules; a manual selection requires an operator adjustment. Skill invocation grants no execution permission.

Establish the imported binary identity, architecture and relevant entry point with the operator-selected healthy adapter's supported operations. Choose identity, imports, exports, strings or functions only as needed for the current question. Use the supplied toolName and environmentId directly; catalog toolId and moduleIds identify different things. If the preferred adapter lacks an operation or fails, retain that limitation before choosing another configured adapter. Feed compatible saved evidenceIds to security_analysis native-triage for a located inventory. Avoid repeating collection when retained evidence already covers the question.

A workspace target is not an imported file asset. For a binary in the selected workspace or source snapshot, read security_help action import-member and import only the exact relative file, then use the returned asset ID with the adapter. Use import for a separate file outside those selected targets when authorized. Query security_capabilities with the relevant toolIds and details only when the supplied route lacks needed information; PATH discovery does not establish which Python environment or adapter dependencies are available. Report an import denial without silently replacing the adapter with equivalent Shell execution.

To investigate a relevant native path, use the preferred adapter's functions and xrefs-to/xrefs-from operations with a located seed. When radare2 evidence is already available, security_analysis native-xref-paths accepts those evidenceIds, a hexadecimal seed, direction callers or callees, and maxDepth. Include strings/imports evidence when relevant. This analysis separates calls, jumps and data references, retains call sites and resolves source functions from explicit adapter ownership or an unambiguous recorded range. Use frontier nextOperation requests to collect missing evidence only for the unresolved question. It returns one discovery path per node, not every possible path. Indirect calls and missing function ranges stay unresolved; no target execution is implied.

Follow a relevant string or imported operation to references, a function and its callers when that can distinguish the competing explanations. Use the preferred adapter's targeted decompilation or disassembly; security_r2ghidra is an alternative when the selected route cannot answer the question. Preserve virtual addresses, file offsets and evidence IDs; do not confuse an address in a loaded process with an unrelocated image address. Imported names and strings are leads, not proof of a reachable defect. Separate observed instructions from decompiler approximations and algorithm hypotheses. This is a choice of checks, not a mandatory sequence for every input.

For cryptographic checks, trace the input encoding, key, nonce, associated data and authentication tag separately, retaining their byte lengths and source locations. Use an available maintained library after inspecting its installed API; do not mix APIs from different libraries or replace a library with a handwritten cipher to work around an argument error. Validate authenticated decryption before interpreting or saving plaintext as a successful result. A failed authentication or digest comparison calls for checking extracted bytes and parameters, not unstructured parameter guessing. A custom implementation requires a demonstrated library gap and independent known-answer tests. Distinguish offline recovery from successful execution and output-file creation by the original program.

For PE address conversion or explicitly requested byte patches, use the bundled [PE helper](pe.md) before writing a parser or patch script. It uses the selected Python's pefile, accepts batches, and saves a patch manifest while returning a compact receipt. Reuse successful results for unchanged inputs and parameters; do not reread full evidence or ask another model to repeat a completed check. Recheck only changed inputs, a failed check or a concrete contradiction. When selecting replacement instructions, account for instruction boundaries, calling convention, stack effects and affected callers. Byte checks and PE checksums do not establish runtime behavior; retain that limitation without adding a mandatory execution or review stage.

For JNI, connect the native symbol or registration to Android-side callers using evidence from each asset. Do not merge findings across different builds or ABIs without an explicit link. Firmware analysis may require security-firmware and Web/IoT modules when the question crosses those components.

Use runtime observation only for a specific unresolved hypothesis after identifying the architecture, dependencies, expected control-flow path and observation point. Prefer debugger/run for a single breakpoint with registers and fixed-length memory: GDB/MI in managed Linux Docker or matching-architecture CDB on Windows. Frida trace capture observes argument values, returns and enter/leave buffers without treating embedded zero bytes as string termination. Use the existing Unicorn route for a bounded instruction slice when full process execution is unnecessary; document initial state, external-call models and coverage limits. Compare any reconstruction with independent original behavior before widening a search. Use security-dynamic’s bounded Frida templates when they fit the question. Prepare and approve the exact script and target through the workbench; do not replace that lifecycle with shell attachment or a watchdog. Findings and independent review remain in the existing evidence workflow.

Read [on-demand tool setup](bootstrap.md) only when a required dependency or operation is missing.
