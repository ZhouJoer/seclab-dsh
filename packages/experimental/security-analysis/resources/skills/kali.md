# Authorized penetration testing (Kali)

Read the task's moduleSelection through security_capabilities. This method needs the pentest module (the web module also enables it); enable reverse.android or reverse.native separately when binary questions arise. In auto mode the coordinator selects relevant modules with security_command action modules. Manual selection belongs to the operator. Explicit skill invocation does not enable a module or approve execution.

Authorization and scope come first. Test only registered, in-scope targets (hosts, domains, ports, accounts, wireless networks) under the engagement's written authorization; the scope is binding and a skill, role or delegated assignment grants no additional authority. Confirm scope, excluded assets, rate limits, lockout policy and maintenance windows before the first packet. High-risk operations — exploitation, credential spraying or brute force, relay and poisoning attacks, deauthentication, persistence, data exfiltration, intrusive checks — require explicit approval through the existing validation-plan workflow. Never start, replace or stop an operator-managed container to make a technique work. On a confirmed critical or high finding, stop the affected branch, notify the operator and wait for direction before escalation.

Select the environment before planning tool use. Inspect candidates with security_environment: a Kali environment is operator-managed (typically a registered docker container with externalContainer), carries measured tool installations and a workdir, and never becomes DSH-owned. Reachability differs per environment: an address reachable from the operator host — especially host-loopback services — may be unreachable from inside a container, and container-side work then needs the environment's host-gateway address; verify from the execution environment, record the working address per environment, and choose the environment that actually reaches the target with the registered tools the question needs. Raw sockets, wireless monitor mode, USB and GPU work need hardware the operator has explicitly provided. Tools registered in a managed environment run through that environment: submit plan commands and execute with security_execute, keep raw outputs in a fresh outputs/ subdirectory of analysisDirectory, and capture committed native calls with security_capture_analysis before citing evidence. For missing tools, follow [on-demand tool setup](bootstrap.md); do not run upstream package managers inside the engagement.

Choose a depth with the operator: Quick (low-noise discovery, top ports, fingerprinting, no intrusive checks), Standard (default: service enumeration, vulnerability scanning, web crawling, reportable evidence), Deep (full ports, selected UDP, authenticated checks, larger wordlists, only on explicit request). Start at Standard and escalate only when results justify it and the operator consents.

Read only the current playbook and the category selection guides it names ([kali/tools/index.md](kali/tools/index.md)); a playbook handoff restarts from the new playbook without pre-reading later phases. Selection guides route to registered tools; per-tool usage follows each catalog entry's guide from security_capabilities rather than this skill. **Open the selected playbook file before the first active probe** — until it is read, limit work to environment inspection and target identity checks. The playbook's early phases run the environment's fingerprinting and scanning tools (whatweb-class inventory, wordlist content discovery, template scanners); generic request tools come into play only for targeted follow-up requests once an endpoint and a hypothesis exist.

Execution standards carry across playbooks. Prefer the healthy registered adapter for an operation — where a semantic security_* tool exists, call it directly instead of a shell equivalent. Run automated scanners before manual probing for each new attack surface, and use the registered specialized tool for its job rather than hand-rolled request loops: technology fingerprinting through a whatweb-class tool, content and parameter discovery through wordlist fuzzers, known-CVE checks through template scanners, with a generic request tool such as curl reserved for targeted single requests once an endpoint and a hypothesis exist. Wordlists come from the execution environment: a container environment ships its own collections (seclists-class paths) — use them in place of the scanner there instead of downloading wordlists onto the operator host, and write a custom script only when no registered tool covers the need. Never treat a scanner match, banner or exit code as a confirmed finding; validate with a second check and preserve the commands, parameters, tool version and raw output as evidence. A clean result from one tool is not proof of absence, and high-speed scans silently drop ports: confirm discovered ports with a slower, higher-retry pass before trusting the inventory. Probe services a scanner labels unknown, tcpwrapped or `?`-suffixed (TLS certificate metadata, ALPN negotiation, banner capture) before marking them unidentified. Test each discovered service through the applicable checks — version, CVE applicability, anonymous access, protocol behavior, credentials within lockout policy, configuration — and record explicit negative results; an untested service is an untested attack surface. When credentials surface in any phase, test them against all in-scope authentication services before continuing. Chain findings into the next playbook only inside the authorized scope.

Record progress in checkpoints at each phase boundary: resolved question, evidence added, deferred items and the return point when a playbook hands off. Raw and derived outputs stay in separate fresh files under outputs/; reuse a saved result only when its input identity, parameters and coverage match. Large outputs go to files with extracted summaries in the tool log, not full dumps into context. On failure, distinguish an unreachable target, an unsuitable tool and a missing capability before retrying; do not repeat an unchanged failing invocation.

Report per the reporting-workflow playbook: scope and authorization statement, environment and tool versions, confirmed findings with severity, reproduction commands and actual output, meaningful negative results, and artifact locations. For Web source and API reasoning, load security-web; for APK or native binaries encountered during an engagement, load security-android or security-native only after the operator enables their modules — this skill does not unlock reverse-engineering tools.
