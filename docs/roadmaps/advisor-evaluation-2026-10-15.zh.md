# Advisor 功能实验评估报告

[English](advisor-evaluation-2026-10-15.md) | 中文

## 摘要

Advisor 的实验已显示出明确的诊断价值：当主模型长期沿着错误前提尝试时，高级模型能够通过独立复核证据，给出可验证的修正方向。当前最明显的不足是主模型不能稳定地主动求助，咨询等待时间波动较大，而且“取得突破”和“完成任务”的判定仍需收紧。

建议继续保留并完善 Advisor，优先解决触发时机、证据交接和完成验收，再评估模型搭配是否带来稳定的时间与费用收益。当前结果支持其作为关键节点的专家复核能力，尚不足以证明开启后就会自动提速或降低总成本。

评估日期：2026 年 10 月 15 日。本文中的 Advisor 指 DSH 当前以 `helper` 工具提供的高级模型咨询功能。

<a id="operation"></a>
## 功能定位与运行方式

Advisor 适合嵌入长链路任务：主模型负责持续执行，顾问负责检查关键判断、解释反复失败的原因，并提出下一步验证方法。顾问返回建议后，主模型仍需执行、验证并交付结果。

当前 Helper 开启后会向主模型提供求助工具。是否调用主要由主模型根据工具说明决定，没有按照失败次数或停滞时间自动触发的程序规则。调用材料包括求助原因、独立完整的问题，以及可选的证据和已尝试方法。每次咨询创建新的顾问上下文，不复制主对话历史。

API 后端通过 DSH 子会话运行，可用工具限定为当前可用的文件读取、文件查找、内容搜索和图片读取。它仍沿用父代理的 preset，并可能接收其中的其他系统说明或动态上下文，因此不等同于一次只含短问题的 API 请求。Codex 后端使用临时只读线程和原生读取能力。两条路径均由顾问提出建议、主模型实施；咨询期间主模型前台等待。

当前实现没有为 Helper 单独规定探索轮数或总等待预算，也没有固定回答格式。工具受限有助于控制行为，但不能保证顾问迅速结束。

<a id="observations"></a>
## 实验中的关键表现

### 独立复核能够打破错误前提

实验任务同时包含定制 UPX 脱壳、加密资源格式分析和 HTTP 页面恢复。难点不只在执行工具，还包括识别被修改的格式字段、准确解释二进制数据，以及选择下一步验证方法。

一次运行中，主模型已累计约 24.5M token，仍未完成脱壳；人工提醒调用高级模型后，脱壳和后续资源恢复得到推进。另一条运行则表明，主模型能够独立完成脱壳，但在资源解密阶段反复尝试，仍需人工提供关键线索。这说明高消耗并不必然带来新证据，局部认知错误可以长期主导后续行动。[实验记录](https://github.com/ZhouJoer/note-gen-sync/blob/main/%E7%BB%93%E6%9E%9C.md)

在可直接追踪建议与后续执行关系的咨询中，顾问重新读取文件，指出实际资源条目数为 190，而主模型一直沿用 63。顾问要求按文件原始字节构造验证输入。主模型采纳后，清单解密立即成功，随后继续恢复资源。这个案例中，顾问的直接贡献是纠正已被当成事实的错误记录。

另一条咨询建议把“能否获得合理明文”和“认证是否通过”拆开检查，帮助主模型缩小失败原因。随后出现了清单明文恢复的进展。顾问在这里提供了更有区分力的验证步骤，而主模型仍承担后续导出和验证。

### 开启功能并不能保证及时求助

多条运行在 Helper 已可用的情况下，仍持续进行字段猜测、组合尝试或环境复查，直到用户明确要求寻找高级模型才发起咨询。也有运行在用户再次提醒“必要时可以求助”后才调用。因此，目前更准确的体验是“具备求助入口”，主动升级的可靠性仍不足。

普通subagent委派也不能替代专家复核。实验记录中出现了委派逆向子任务、但未调用 Helper 的行为；工作被分配出去，并不意味着关键假设接受了更强模型的审查。

### 工具环境影响了大量无效工作

会话中出现了已有本地工具却继续寻找其他安装方式、选中缺少依赖的可执行文件、等待安装，以及反复检查不可用运行环境等情况。明确本地工具位置、修正工具适配器和整理项目资产后，部分运行明显减少了前期探索。

较低的一次会话累计显示为 18.5M token，但其间仍有人工提示和顾问调用，工具与资产配置也已变化。该结果说明整体工作流存在改善空间，不能单独归因于某个模型或自动求助策略。

<a id="latency"></a>
## 等待时间与交互成本

顾问咨询的等待时间差异较大，已经影响到用户是否愿意继续等待。

| 咨询情形 | 观察到的等待 | 后续表现 |
| --- | --- | --- |
| API 顾问等待后被人工停止 | 实验笔记记录约 414 秒 | 当次咨询被中断，不能据此判定最终建议是否有效 |
| 后续改用 Codex 顾问复核字段 | 调用卡片记录 233.2 秒 | 纠正条目数等前提，主模型随后成功解出清单 |
| 另一条成功的顾问咨询 | 调用统计记录 802.4 秒 | 给出新的诊断方法，后续取得清单恢复进展 |

等待时间包含顾问推理、可能的文件读取、多轮模型请求及后端开销。当前证据不能把延迟全部归因于模型生成速度，也不能证明 API 后端天然比 Codex 后端慢。上述样本的问题材料、模型配置和运行阶段并不相同。

取消并不代表整个任务失败。被停止的 API 咨询所在会话，之后改用 Codex 顾问继续推进，最终会话报告记载了 190 个资源通过认证解密。评价应分别记录单次咨询是否返回、建议是否有效，以及整个任务最终完成到哪一步。

顾问在前台运行时，用户需要看见当前阶段与已等待时间，并能取消。更实用的设计是提供快速诊断和深入复核两种可配置方式：前者集中审查已有证据，后者允许有目标地补充读取。两者都应有明确的时间、token 或探索轮数预算。

<a id="acceptance"></a>
## 成本与完成标准

### 累计 token 不能直接代表效率收益

实验涉及 DeepSeek-V41-Flash、GLM-5.3-Flash 以及不同的高级模型后端。运行期间还发生了人工纠错、工具配置优化、资产整理和中断续跑，因而不能把各会话总量作为模型能力排行榜。

复核时，相关会话显示的缓存命中率约为 95% 至 97%。界面中的百万级累计 token 包含反复请求的上下文，既不等于生成了同等数量的新内容，也不等于最终账单。顾问统计还应与主模型统计分别核对，避免遗漏子会话用量或重复计算。

部分本地会话在实验笔记记录后继续运行，累计量和完成状态已有变化。后续比较应固定观察截止点，分别统计首次有效突破前的用量、咨询本身的用量，以及完成验收前的总用量。

### 应把完成拆成可验证的阶段

现有记录中的“完成”覆盖了不同程度的结果。报告和界面需要明确区分：

1. 服务程序已脱壳，可以继续静态分析。

2. 已恢复清单明文，可以解析资源记录。

3. 已导出全部资源，并完成数量、长度、格式或解压校验。

4. 加密认证标签已验证通过。

5. 静态页面可通过 HTTP 访问。

6. 原始服务运行正常，动态模板和接口行为经过验证。

已有运行记录了全部 190 个资源导出及静态 HTTP 返回成功，但同时明确保留了认证标签未通过、原始 ARM 服务未运行等限制。另有运行记录了全部资源通过认证解密。两者的验收程度不同，静态页面可访问也不能直接等同于原始服务完整恢复。

在一条较晚的运行中，顾问已成功返回建议，主模型随后报告恢复了清单明文，但仍明确表示尚未导出全部资源；此时会话累计显示为 41.9M token。该运行应记为“顾问促成关键进展”，不宜记为完整交付成功。

会话还出现过用户追问后，主模型承认把原本明文可读的头部字段误写成已解密结果的情况。因此，Advisor 除了在卡住时介入，也适合在主模型准备宣布完成时复核证据与验收范围。

<a id="comparison"></a>
## 与现有 Advisor 设计的关系

Claude Code 官方文档将 Advisor 定位为在方案选择、反复失败和完成检查等关键节点提供第二意见。其调用时机同样由主模型决定，但顾问接收完整对话，包括工具调用与结果。DSH Helper 则由主模型整理本次问题与证据，再交给独立顾问；API 路径还允许有限的文件读取。[Claude Code Advisor 文档](https://code.claude.com/docs/en/advisor)

两种上下文方式各有取舍。完整历史保留了失败过程，但会带来更多输入；问题摘要更紧凑，却可能把主模型的错误判断包装成确定事实。此次条目数纠错说明，顾问应能核对关键原始证据，提交材料也应区分“观察事实”“尚未验证的解释”和“希望顾问判断的问题”。

<a id="priorities"></a>
## 功能改进优先级

### 先提高求助触发的可靠性

在主模型系统提示词中明确列出应当求助的情况：同一障碍经过不同尝试仍无进展；准备重复失败方法却没有新证据；观察与既有结论冲突；准备宣告受阻或完成，但关键判断尚未得到验证。

仅靠提示词仍不能保证调用。若产品需要稳定的自动升级，可增加可配置的停滞检查点，在满足条件时要求一次专家复核，并记录触发原因。普通subagent调用不应计入这项复核。

可采用以下主模型指引作为后续实验起点：

> 当 Advisor 可用时，同一障碍经过两次实质不同的尝试仍无新证据，或下一步只是重复失败方法，应先提交专家复核。提交目标、原始证据、已尝试方法与结果，并把已确认事实和当前假设分开。不要仅凭多次失败就宣布某条路线不可能。收到建议后先执行最小验证，根据结果决定是否继续，并更新任务状态。

“两次”是待验证的触发参数，应随误触发率、停滞长度和任务结果调整。

### 让顾问优先纠正判断

提交材料应包含明确的决策问题、必要原始证据、失败记录、环境约束和验收条件。顾问先指出最值得复核的前提，再给出一个能够区分不同原因的最小验证步骤；需要更多材料时，明确指出缺失的证据。

API 顾问可采用专用的精简提示词组合，减少与只读咨询无关的主代理说明，同时保留必要的权限约束和工作区信息。顾问输出宜围绕结论、依据、最小验证、预期结果和未决问题组织，避免把咨询扩展成另一条无明确终点的执行任务。

### 把工具配置变成稳定输入

为主模型明确提供已验证的工具路径、能力、依赖状态和适用环境。优先使用已配置且可用的工具；只有现有工具无法覆盖需求时，才寻找替代方案。验证失败应产生具体诊断，避免模型因错误路径或不完整错误信息而重新安装、切换工具或重复探测。

### 闭合建议与结果的记录

当前“顾问成功”只表示咨询正常结束，尚不能说明建议被采纳或确实解决问题。应补充记录建议是否执行、最小验证结果、是否产生新证据，以及最终完成阶段。同时，在取得新进展后更新旧的受阻状态，避免界面仍显示已被后续证据推翻的阻塞判断。

<a id="evaluation"></a>
## 后续评估方法

下一轮应固定任务文件、工具安装、资产配置、主模型、推理强度与验收标准，隔离历史产物，并对相同条件重复运行。可比较不开启顾问、主模型自行求助、明确触发提示和程序检查点四种方式；另外用相同问题与证据单独比较顾问后端的延迟和建议质量。

主要指标应包括：

- **介入及时性**：从出现重复失败到求助的时间、步骤数，以及是否需要人工提醒。

- **建议有效性**：是否发现新的事实或错误前提，主模型执行后是否取得可验证进展。

- **完整交付**：按分阶段验收标准记录结果，不能以模型自述完成代替验证。

- **等待与中断**：咨询耗时、取消比例、返回后到下一次有效进展的时间。

- **全链路成本**：主模型与顾问分别统计输入、缓存、输出和实际计费，并与任务完成程度一起比较。

优先验证的是 Advisor 能否减少无进展的重复尝试和人工纠错，同时保持交付质量。只有在一致条件下观察到稳定收益，才能进一步确定默认触发策略、预算和模型搭配。
